## 0. What "production level app" means for this project, concretely

Not just "add more screens." Specifically:
1. **Real backend integration**, not mock data, for every shipped feature — the mock pattern in `AuthRepositoryMock` was a bridge for *before* the backend repo was available; it isn't the target state.
2. **Typed error handling end-to-end** — every failure a user can hit resolves to an `AppException` the UI renders meaningfully, never an uncaught exception or a raw JSON blob on screen.
3. **A test per feature** — unit (provider/repository logic), widget (screen states: loading/empty/error/success), and an integration smoke test for the multi-step flows that matter (login, mark attendance, submit an assignment).
4. **Environment-safe builds** — `main_dev.dart` / `main_staging.dart` / `main_prod.dart` are the only three ways this app should ever be built; no hardcoded URLs, no secrets in source.
5. **Role-correct navigation enforced in the router**, not just hidden UI — matches `feature_matrix.md`'s CRUD boundaries, understanding those are also meant to be enforced server-side (not fully verified yet, see `api_spec.md` §12 row 7 and `implementation_plan.md` Phase 11).
6. **Nothing invented** — every field name, endpoint path, and business rule traces to a citation in `api_spec.md` or an explicit product decision recorded in §4 below. Where the backend doesn't support something (Online Classes, push notifications, Teacher notice creation), the app doesn't pretend it does.

## 2. Local backend — DONE (2026-08-23)

Completed. See `docs/local_backend_setup.md` for the concrete record: where it's cloned, `.env` contents, how to start/stop it, and the seeded accounts (SuperAdmin/Admin/Teacher/Student/Parent, one Class+Section) every feature phase below should build and test against. The steps that produced it are kept below for reference / re-doing on a fresh machine.

1. **Move the backend out of scratch.** It's currently in a session-ephemeral scratchpad directory that will not survive past this session. Decide with the user where it lives permanently — a sibling directory next to this Flutter project (e.g. `../cloud_lms_backend/`) is the common pattern; it should **not** live inside `lib/` or anywhere Flutter tooling scans. Do a fresh `git clone https://github.com/ArbindDas/SujalbackendForStudentmanagement.git` there rather than copying the scratch checkout.
2. **Install Node dependencies**: `npm install` (package.json confirms Express 5, Mongoose, Socket.IO, Cloudinary, Multer, Resend, etc. — see `api_spec.md` §10).
3. **A local MongoDB instance** — either `docker run -d -p 27017:27017 --name cloudslms-mongo mongo` or a local install. A free MongoDB Atlas cluster also works if Docker isn't available.
4. **Create a `.env` file** (gitignored, confirmed by `.gitignore` inspection) with every variable the backend code actually reads — this list is exhaustive, taken directly from grepping `process.env.*` across the source, not guessed:

   | Variable | Purpose | Local-dev-safe value |
   |---|---|---|
   | `PORT` | listen port | `4000` (confirmed default) |
   | `NODE_ENV` | env flag | `development` |
   | `MONGO_URI` | Mongo connection string | `mongodb://localhost:27017/cloudslms_dev` |
   | `JWT_SECRET` | access-token signing | any random string for local dev |
   | `REFRESH_TOKEN_SECRET` | refresh-token signing | any random string, **different** from `JWT_SECRET` |
   | `FRONTEND_URL` | used in email templates/links | `http://localhost:5173` |
   | `BASE_URL` | used in email templates/links | `http://localhost:4000` |
   | `SUPERADMIN_EMAIL` | seed script target | `super@school.com` (matches `seedSuperAdmin.js`) |
   | `QR_SECRET` | QR-attendance token signing | any random string |
   | `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET` | file uploads | **needs a real (free-tier) Cloudinary account** — nothing uploads without these |
   | `RESEND_API_KEY` | transactional email | **needs a real (free-tier) Resend account** — OTP/notice/notification emails silently fail without it |
   | `EMAIL_USER` | referenced alongside Resend setup | your Resend-verified sender address |
   | `ESEWA_MERCHANT_ID` / `ESEWA_PAYMENT_URL` / `ESEWA_SECRET_KEY` | fee-payment QR/branding display only (not a live gateway call — see `api_spec.md` §10) | sandbox/placeholder values are fine, this isn't called server-to-server |

   Cloudinary and Resend are the two you can't fully fake — if a feature you're building doesn't touch uploads or email, the app will run fine without valid values for those, but will throw when it hits code paths that do.
5. **Seed a SuperAdmin**: `node seedSuperAdmin.js` (confirmed to create `super@school.com` / `super123` in the `User` collection).
6. **Start the server**: `npm run dev` (nodemon) or `node server.js`. Confirm `GET http://localhost:4000/health` returns `{"status":"OK",...}`.
7. **Walk the real onboarding flow once, by hand** (via Postman/curl, or once Phase B's Admin screens exist, via the app itself), matching `product_requirements.md` §2 / `user_flows.md` Flow 3: log in as SuperAdmin → create a School → create/approve a Subscription (the confirmed `POST /api/subscriptions/demo` endpoint is the literal "7-day free demo" backend) → create an Admin for that school → log in as that Admin → create at least one Class/Section, one Teacher, one Student, one Parent. This seed data is what every feature phase below gets built and tested against.
8. **Point the Flutter app at it**: `flutter run -t lib/main_dev.dart --dart-define=BASE_URL=http://localhost:4000` from a simulator/desktop. **Note for a physical device or Android emulator**: `localhost` resolves to the device itself, not your machine — use your machine's LAN IP, or `10.0.2.2` for the Android emulator specifically.

### Phase A — Auth, for real — DONE (2026-08-23)
**Backlog**: `E1`. **Plan**: Phase 3, completion.

All five steps done: `AuthRepositoryHttp` wired in (mock deleted), `LoginScreen` shows `ValidationException.fieldErrors` alongside `.message`, single-flight refresh-on-401 (`TokenRefreshInterceptor`), `restoreSession()` persists the login-time `AppUser` via `LocalPrefsService.cachedUserJson` (JSON string — kept feature-model-free so `core/` never imports a `features/auth` type) alongside the tokens, and an `AuthRepositoryHttp` test suite using a fake `Dio` `HttpClientAdapter` (`test/unit/features/auth/auth_repository_http_test.dart`) plus a `TokenRefreshInterceptor` test suite (`test/unit/core/token_refresh_interceptor_test.dart`).

**Acceptance verified for real** (not just unit tests) against the seeded Admin from `docs/local_backend_setup.md`, live in Chrome (`flutter run -d chrome --web-port=5173`, port matched to the backend's allowed CORS origin):
- Log in as `admin@greenwood-demo.test` → lands on the Admin dashboard. Confirmed by the user.
- Reload the page → session persists, stays on the dashboard. Confirmed.
- Log out → returns cleanly to the login screen. Confirmed.

**Two real bugs found and fixed along the way, not scope creep — both were pre-existing, this was just the first time the app had ever actually been run live** (the integration test can't execute in this sandbox without full Xcode, and unit tests never exercised the two things below in combination):
1. **`TokenRefreshInterceptor`'s `_refreshDio` used its own default (real) `HttpClientAdapter`** instead of sharing the main `Dio`'s — meaning the refresh call would have gone out over a real, unfaked/unconfigured network stack even in tests, and more subtly, was just architecturally wrong (two separate HTTP transports for one app). Fixed by sharing `dio.httpClientAdapter`. Caught by `token_refresh_interceptor_test.dart` before it ever shipped.
2. **`app_router.dart`'s `_redirect` bundled splash into the same "already a valid resting place" check as login** for `AuthStatus.unauthenticated` — so a freshly restored, logged-out session never redirected off the splash/loading screen at all; the app just hung there forever. This is what "the chrome browser is only showing a loading indicator" turned out to be. Fixed by giving splash special handling (only login is a valid unauthenticated resting place). Added `test/widget/core/app_router_test.dart` (didn't exist before) covering this exact regression end-to-end through the real router.

Macos desktop can't be used to verify any of this locally — `flutter run -d macos` fails (`xcrun: error: unable to find utility "xcodebuild"`, only command-line tools are installed, not full Xcode) — same known gap `docs/production_roadmap.md` §1 already flagged for the integration test. Chrome web was the only available live target; `flutter_secure_storage`'s web implementation was suspected first (it's explicitly flagged "experimental" in its own README) but turned out to be a red herring — the real bug was in this app's own router.

### Phase D — Assignments — core scope DONE, live-verified (2026-08-23/24)
**Backlog**: `E4`. **Plan**: Phase 6.
**Decision resolved 2026-08-23 — user confirmed System A** (`/api/assignments`) — the only one with submission + grading, matching the product doc's actual module. System B (`/api/teachers/assignments`) is out of scope, not integrated against.

New `features/assignments/` module. Key finding that shaped the whole build: `GET /api/assignments` is **one endpoint shared by all four roles**, scoped entirely server-side by the caller's token (Teacher → own assignments, Student → own class's active ones, Parent → union of all children's classes' active ones, Admin → whole school) — so unlike Attendance, this didn't need a role-split provider; one `AssignmentProvider` covers list/detail/create/edit (Teacher), submit (Student), and grade (Teacher), all backed by one `AssignmentRepository`. This is also the first route in the router genuinely shared across all four roles (`/assignments`, outside every role-prefix segment) rather than living under `/admin/...`/`/teacher/...`/etc. — `_roleFor()`'s comment in `app_router.dart` was updated to explain why that's correct instead of a gap.

1. **Teacher: Create/Edit — DONE.** `class`/`section` submitted as plain-text names via a picker sourced from the app-wide `AcademicStructureProvider` singleton, not `sectionId` — deliberately: the `sectionId` path in `createAssignment` gates on the teacher actually being in `Section.teachers` (`Section.service.js`'s `assertTeacherInSection`), which nothing in Phase B ever populates, so it would 403 for every seeded teacher. Edit mode shows class/section read-only (the repository's `updateAssignment` doesn't expose changing them). **Delete is deliberately not built** — `implementation_backlog.md` E4-F1-T3 already flagged this as unresolved (`DELETE /:id` has no visible role check at the routing layer per `api_spec.md` §12 #7), so it stays parked pending that clarification, same call the backlog already made.
2. **Teacher: Grade Submissions — DONE.** Submissions list per assignment with a marks+remarks grade dialog; once `gradedAt` is set the backend locks it, matched client-side by hiding the Grade button.
3. **Student: View & Submit — DONE.** Submit form (text + up to 5 files via `file_picker`, reusing the same package/pattern as Students' bulk-import) that becomes a graded-result view once `gradedAt` is set. The three confirmed submission rules (first submission blocked past due date; resubmission allowed any time before grading; locked once graded) surface as backend error messages rather than being re-validated client-side, since the backend is the source of truth for all three.
4. **Parent: read-only view — DONE.** No separate screen — the shared `AssignmentDetailScreen` simply renders no submission section for `AppRole.parent`/`AppRole.admin`, since `getAssignmentSubmissions` is Teacher-only server-side and there's nothing else to call for those roles.

**Real bug found and fixed, cost significant time — worth remembering**: a widget test wrapping `AuthProvider` (whose constructor kicks off an async `restoreSession()`) hung the *entire test process* (not just the test — `flutter test` itself never exited) when the test tried to flush that async work with a real `await Future<void>.delayed(Duration.zero)` before `pumpWidget`. Root cause: `testWidgets`' `AutomatedTestWidgetsFlutterBinding` fake-clocks time, so a real `Timer`/`Future.delayed` never fires without an explicit `tester.pump(duration)` — the await hangs forever, and because it hangs *before* `pumpWidget` even runs, none of the usual `pumpAndSettle`-timeout diagnostics catch it either. Fixed by constructing `AuthProvider` synchronously and letting the test's own subsequent `pumpAndSettle()` (which properly drains both fake-clock timers and microtasks) settle the async restore — matching the pattern `app_router_test.dart` already used successfully. **Never `await Future.delayed(...)` inside a `testWidgets` body** — this applies to any future test combining `AuthProvider` (or anything else with an unstoppable async constructor side effect) with the widget test harness.

Test coverage: 200/200 total passing at the time (repository, provider, and widget tests — including role-aware FAB/detail-body variants — for every new piece), `flutter analyze` clean. **Live-verified in Chrome by the user (2026-08-24)** — create/edit/grade/submit all passed against the seeded Teacher/Student/Parent accounts. **Known local limitation, confirmed during this pass**: Cloudinary credentials are empty in `.env` (`docs/local_backend_setup.md`), so the file-attachment path in Student submission fails server-side until a real Cloudinary account is configured — text-only submissions work fine, as expected.

**Real bug found and fixed during this live-verification pass (2026-08-24), not caught by any test**: the Teacher-facing Class/Section pickers in `AssignmentFormDialog` called `GET /api/classes` via `AcademicStructureProvider` — an endpoint guarded by `protectAdmin`, which 401s for a Teacher token. This left the Class dropdown silently empty for the one role that actually uses this form (nothing in the existing test suite caught it because the widget tests mocked `AcademicStructureProvider` directly, bypassing the real auth-guard mismatch). Fixed by sourcing the pickers from `GET /api/sections/my/teacher` (`AttendanceRepository.getMySections()`, the same Teacher-eligible endpoint Attendance's Mark Attendance screen already used successfully) instead — one fetch now covers both Class and Section names, with a visible inline error on failure instead of a silent empty dropdown. Test suite updated to mock `AttendanceRepository` via the service locator and cover the error case; 258/258 passing after the fix.
1. Teacher create/edit (title, description, subject, due date, optional attachment).
2. Student view + submit (up to 5 files via the confirmed `documentUpload` Cloudinary config, blocked past due date on first submission, resubmit allowed until graded).
3. Teacher grade (numeric `marks` + `remarks` — confirmed, not a checked-flag).
4. Parent read-only view.

## 5. Per-feature build checklist

Repeat this for every vertical slice in §3 — it's the same shape every time, which is the point:

1. **Confirm the exact contract** in `api_spec.md` (path, method, body, response) before writing a model. If it's one of the handful of areas flagged `UNKNOWN — VERIFY` (see `api_spec.md` §11) or not yet deep-dived (like Classes/Sections, §3 Phase B note above), do a quick targeted read of that route file first — same read-only method as the original backend pass, not a guess.
2. **Models** in `features/<module>/data/models/` — field names and types match the confirmed JSON shape exactly, not the Mongoose field names 1:1 where they differ (e.g. `_id` → `id`).
3. **Repository**: abstract interface in `data/repositories/`, one `Http` implementation. **Skip building a new Mock** — that pattern existed only for the pre-backend-access period; the local backend from §2 is your "mock" now, and building against it directly is more honest than maintaining two implementations that can drift.
4. **Provider**: one `ChangeNotifier` per feature holding loading/data/error state, added as one more line to `app.dart`'s `MultiProvider` list — never merged into `AuthProvider` or any shared provider.
5. **Screens**: per that module's entry in `screens.md`, using `LoadingView`/`EmptyStateView`/`ErrorView` from `shared/widgets/` for every loading/empty/error state — don't build bespoke ones per screen.
6. **Router**: add routes to `app_router.dart`/`app_routes.dart` with the correct role restriction, following the existing `_roleFor()` pattern (or generalize it to a lookup table once there are more than a handful of routes — the foundation's switch-statement approach was deliberately left simple for exactly 4 placeholder routes, not meant to scale past that as-is).
7. **Tests**: repository test against a fake `Dio` adapter (no real network), provider test with a mocked repository via `mocktail` (follow `auth_provider_test.dart`'s pattern exactly), widget test for the screen's loading/empty/error/success states.
8. **Cross-check** against that role/feature's row in `feature_matrix.md` before calling it done — especially any cell marked `CONFLICT` or `CONFIRMED` with a caveat.
9. `flutter analyze` + `flutter test` clean before moving to the next feature. No exceptions.
