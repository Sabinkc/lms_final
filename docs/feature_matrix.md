## Notes
- "Oversight" R for Admin on Assignments reflects a real, confirmed role-aware `GET /api/assignments` (Admin sees all in school) — no longer an inference from doc prose. The equivalent "oversight" claims for Chat and Online Class Links did **not** hold up: Chat has no Admin-facing endpoint at all, and Online Class Links has no backend of any kind (see rows above).
- Assignment **submission** is `C` (a separate `AssignmentSubmission` document, unique on `assignmentId`+`studentId`) — confirmed to match the real data model, not just a UI convention.
- No feature gives **Parent** any write (C/U/D) access beyond their own profile **except fee payment submission**, now confirmed real (see Fee Payment row). The original doc's "parents are read + chat only" turns out wrong on both halves: Parents have **zero** chat access (not read-only — none), and now have **one** real write action outside their profile (submitting a payment).
- Delete (`D`) for Admin is still asserted by convention on most entities; `api_spec.md` didn't trace every `DELETE` route's role guard exhaustively, so soft-delete vs. hard-delete behavior remains `UNKNOWN — VERIFY` per-entity.
- **Attendance is fragmented across ~10 backend models** (separate Student/Teacher/Staff attendance, plus Session/Record/Correction/Log/Settings/WeeklyRegister/TeacherAssignment models) — the row above describes *student* attendance only, matching this product doc's scope. A Teacher's own attendance is a completely separate, Admin/HR-marked model with no self-edit rights (only a one-time daily self-check-in) — not given its own row here since it's outside the original 4-role product scope, flagged so it isn't confused with the student-attendance row above.
- **Two parallel Assignment systems exist in the backend** (`api_spec.md` §4.5): the row above describes System A (`/api/assignments`), which matches this product doc's module. A second, independent System B (`/api/teachers/assignments`) also exists — admin-created only, list/delete, **no submission or grading endpoints** — and it's `UNKNOWN — VERIFY` which system (or both) the mobile app is meant to integrate against.
- Prior-pass conflicts (Teacher assignment-delete, Admin notice-edit/delete affordance) flagged in `gap_analysis.md` §4 are now backend-confirmed findings rather than open UI-vs-matrix disagreements — see the Assignments and Notices rows above and `api_spec.md` §12 rows 6–7 for the resolved/still-open status of each.
